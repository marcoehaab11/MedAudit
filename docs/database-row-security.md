# حماية سجلات قاعدة البيانات

هذا التغيير يضيف RLS: قواعد داخل PostgreSQL تمنع قراءة السجل أو تغييره خارج النطاق المسموح. بيانات المرضى مشتركة بين فريق العيادة حسب صلاحيات التطبيق، وليست حكرًا على الموظف الذي أنشأها. الإشعارات الشخصية والتفضيلات تخص صاحبها.

## ما تغير

- تفعيل وإلزام RLS على جميع الجداول الـ88 الموجودة في نموذج التطبيق وملفات إنشائها.
- إضافة أربع سياسات لكل جدول: `row_read` للقراءة، و`row_insert` للإنشاء، و`row_update` للتعديل، و`row_delete` للحذف. سياسة التعديل تفحص السجل قبل التعديل وبعده؛ لا يكفي السماح بقراءة السجل لتغيير مالكه.
- إضافة عشر سياسات محددة للحجز العام؛ العدد الإجمالي 362 سياسة.
- التحقق من عضوية المستخدم الفعالة وربطها بحساب تسجيل الدخول والعيادة في قاعدة البيانات. تؤخذ الهوية من الجلسة التي تحقق منها الخادم؛ لا تؤخذ من جسم الطلب أو معرّف يرسله المتصفح.
- منع مستخدم عادي من تعديل الأدوار والصلاحيات. تُقرأ صلاحية `Users.ManageRoles` من قاعدة البيانات، بما فيها أي ملف صلاحيات مخصص.
- منع تغيير حساب الهوية المرتبط بعضوية موظف، أو تغيير العيادة الأم، بواسطة مشغلين عاديين. هذان فحصان إضافيان داخل قاعدة البيانات باسمَي `protect_membership_identity` و`protect_clinic_parent`.
- فصل تشغيل التطبيق عن تحديث هيكل قاعدة البيانات. لا يملك حساب التطبيق الجداول، ولا يستطيع تجاوز RLS أو إنشاء أدوار.
- إيقاف بدء التطبيق إذا كان الاتصال فائق الصلاحيات، أو يستطيع الوصول إلى دور يتجاوز الحماية، أو كان هناك جدول مستخدمين غير محمي في مخطط `public`.
- لا توجد حزم جديدة أو ترقيات للحزم، ولا تغييرات في الشاشات.

لا يوجد Supabase هنا، وبالتالي لا توجد مفاتيح anon أو service-role. تبقى كلمة مرور مالك PostgreSQL في خدمة قاعدة البيانات وخدمة التحديث المؤقتة فقط؛ لا تُعطى لخدمات الويب أو لوحة الإدارة أو العامل الخلفي.

## السياسات الخاصة

| السياسة | الجدول | السماح المحدود |
|---|---|---|
| `public_patient_insert` | `patients` | إنشاء ملف جديد بمعرّف أنتجه الخادم وببيانات الحاجز |
| `public_appointment_insert` | `appointments` | إنشاء الحجز الجديد المحدد في نطاق الطلب |
| `public_appointment_update` | `appointments` | تعديل حجز يُسمح بإدارته؛ لا يسمح بتغيير عيادته أو مريضه أو طبيبه إلى سجل آخر |
| `public_inquiry_insert` | `booking_inquiries` | إنشاء الاستفسار المحدد في الطلب |
| `public_visit_insert` | `booking_page_visits` | تسجيل زيارة صفحة العيادة العامة |
| `public_idempotency_insert` | `public_booking_idempotency_records` | حفظ مفتاح منع تكرار الحجز الخاص بالطلب |
| `public_sequence_insert` | `patient_number_sequences` | بدء تسلسل أرقام المرضى للعيادة العامة المحددة |
| `public_sequence_update` | `patient_number_sequences` | حجز الرقم التالي للعيادة المحددة |
| `public_delivery_insert` | `notification_deliveries` | تجهيز إشعار عن الحجز أو الاستفسار المسموح به |
| `public_outbox_insert` | `outbox_messages` | وضع إشعار الحجز في قائمة الإرسال للعيادة المحددة |

الحجز العام لا يقرأ كل المواعيد لحساب الإتاحة. الدالة `clinic_security.busy_periods` تُرجع الأوقات المشغولة فقط، دون أسماء المرضى أو ملفاتهم. إدارة الحجز تعتمد على بصمة سر الإدارة، وليست على رقم الحجز وحده.

رقم الهاتف المكتوب في نموذج عام لا يثبت ملكية ملف طبي قديم. لذلك لم يعد الحجز العام يربط الزائر تلقائيًا بملف قديم يحمل الرقم نفسه. ينشئ ملفًا بالبيانات المدخلة، ويجب على الموظف التأكد من الهوية قبل تسوية أي تكرار. هذا يمنع كشف اسم المريض القديم أو ربط حجز شخص آخر بملفه بمجرد تخمين هاتفه.

الجدول التقني `__EFMigrationsHistory` يسجل أسماء تحديثات قاعدة البيانات، ولا يحمل بيانات مستخدمين. لم يُفعّل عليه RLS؛ حساب التشغيل يستطيع قراءته فقط، لأن النسخ الاحتياطي يحتاج معرفة إصدار الهيكل، ولا يستطيع تعديله.

## الحسابات والسياق

| الحساب أو الدور | الاستخدام |
|---|---|
| مالك PostgreSQL الحالي | خدمة `migrate` المؤقتة لتحديث الهيكل؛ لا يستخدمه التطبيق أثناء خدمة الزوار |
| `meddentist_app` | خدمات الويب ولوحة الإدارة؛ عضو في دور `meddentist_runtime` المحدود |
| `meddentist_jobs` | خدمة التذكير والإرسال؛ عضو في `meddentist_runtime` و`meddentist_worker` |
| `meddentist_worker` | قراءة الجداول المطلوبة للتذكير فقط، وكتابة سجلات الإرسال والإشعارات؛ لا يسمح بحذف المرضى أو قراءة كلمات المرور |

قبل كل استعلام، يستبدل الخادم جميع قيم سياق الهوية، بما فيها القيم الفارغة. داخل معاملة قاعدة بيانات، أي مجموعة عمليات تُنفذ معًا، تكون القيم محلية لتلك المعاملة. خارجها تُستبدل قبل كل أمر، وتُصفّر عند إعادة الاتصال إلى مجمع الاتصالات. يُرفض إعداد الاتصال إذا عطل التصفير أو سمح بتوزيع أوامر الطلب على اتصالات مختلفة.

مسارات التحقق من كلمة المرور والرموز تستخدم نطاق هوية مؤقتًا على الخادم. يسمح هذا النطاق بعمليات الهوية المطلوبة، ولا يسمح بقراءة المرضى أو السجلات الطبية أو المالية. تسجيل عيادة جديدة يستخدم نطاق إنشاء يحدد العيادة الجديدة. الفروع تتطلب الصلاحية من قاعدة البيانات، وتبقى مقيدة بالمجموعة نفسها. نطاق البريد ومراقبة الخدمة لا يمنح الوصول إلى ملفات المرضى.

قاعدة البيانات تثق بالخادم في إثبات الهوية. كلمات مرور اتصال قاعدة البيانات أسرار للخادم؛ هذه الآلية ليست حماية من شخص يملك كلمة مرور تشغيل الخادم نفسه أو حساب `postgres`. مدير المنصة وخدمة النسخ الاحتياطي المصرح بها والعامل الخلفي لهم وصول مقصود حسب وظائفهم.

## التشغيل الآمن

التغيير جاهز كملف ترحيل، أي ملف يغير إعدادات قاعدة البيانات بطريقة مسجلة. لم يُطبق على قاعدة الإنتاج من هذه البيئة. Docker لم يكن متاحًا هنا.

1. احتفظ بنسخة احتياطية حالية من قاعدة الإنتاج قبل النشر.
2. في ملف `.env` على السيرفر، أضف كلمتي مرور عشوائيتين مختلفتين، لا تقل كل منهما عن 32 حرفًا: `DATABASE_APP_PASSWORD` و`DATABASE_WORKER_PASSWORD`. تم توليد قيمتين آمنتين بالفعل في ملف `.env` المحلي، دون طباعتهما أو إضافتهما إلى Git. لا تحتاج إنشاء حساب لدى خدمة خارجية.
3. ابنِ الصور الجديدة قبل إيقاف الخدمات:

   ```sh
   docker compose build api platform-admin worker migrate
   ```

4. استخدم نافذة صيانة قصيرة: يجب ألا يستمر الكود القديم بالعمل أثناء التحويل إلى حسابات التشغيل المحدودة.

   ```sh
   docker compose stop api platform-admin worker
   docker compose up -d postgres redis
   docker compose run --rm --no-deps migrate
   ```

5. إذا نجحت خدمة التحديث فقط، شغّل الخدمات الجديدة:

   ```sh
   docker compose up -d api platform-admin worker
   ```

6. اختبر تسجيل الدخول والحجز العام والعزل كما هو موضح أدناه، وتأكد من عدم وجود أخطاء صلاحيات في سجلات العامل الخلفي.

خدمة `migrate` تستخدم كلمة مرور المالك الموجودة بالفعل في `POSTGRES_PASSWORD`، وتتحقق من وجود كلمتي المرور الجديدتين قبل تطبيق تحديثات الهيكل، ثم تنشئ حسابي التشغيل أو تحدث كلمتي مرورهما. يجب أن يستخدم الترحيل حساب المالك المميز الخاص بإعداد PostgreSQL الحالي؛ تتوقف العملية إن كان حسابها غير مناسب. وظائف التحقق داخل القاعدة تعمل بصلاحية مالكها، مع قصر تنفيذها على حسابات التشغيل ودون إعطاء هذه الحسابات صلاحية المالك. إعداد Compose يجعل الخدمات تنتظر نجاح التحديث. عند تشغيل الخدمات، قد تعيد Compose تشغيل خدمة التحديث المسماة أيضًا؛ التحديثات المسجلة لا تُطبق مرتين، ولا تُعاد كتابة البيانات القديمة.

تفعيل RLS دون سياسة تسمح بالوصول يعني المنع افتراضيًا. ملف الترحيل يجهز القواعد والحسابات والسياسات والتفعيل داخل معاملة واحدة. ويتوقف إذا وجد سياسات قديمة غير متوقعة، بدل توسيعها أو مسحها دون مراجعة. لا توجد عملية تراجع تلقائية تزيل حماية البيانات؛ فشل التحديث يستلزم مراجعة سببه قبل إعادة تشغيل الكود القديم.

للتشغيل خارج Compose، نفذ `DentalClinic.Api --migrate` باتصال المالك وكلمتي المرور الجديدتين ضمن إعدادات `DatabaseSecurity:AppPassword` و`DatabaseSecurity:WorkerPassword`، ثم شغّل الويب باتصال `meddentist_app` والعامل باتصال `meddentist_jobs`. لا تضع اتصال المالك في عملية الويب طويلة التشغيل.

## اختبارات يمكنك تنفيذها

1. أنشئ مستخدمًا **أ** في عيادة تجريبية، ومستخدمًا **ب** في عيادة تجريبية مختلفة. امنحهما صلاحيات إضافة المرضى وقراءتهم وتعديلهم، وأنشئ مريضًا في كل عيادة.
2. ادخل بحساب **أ** وافتح مريضه من قائمة المرضى. انسخ المعرّف الموجود بعد `/patients/` في رابط الصفحة.
3. افتح نافذة خاصة وسجل دخول **ب**. افتح مريضه ثم استبدل معرّفه في الرابط بمعرّف مريض **أ**. يجب ألا تظهر بيانات **أ**؛ طلب البيانات سيعود بحالة `404`، أي «السجل غير موجود».
4. من نافذة **ب** نفسها، افتح رابط `/api/patients/معرّف-مريض-أ` على نطاق التطبيق. يجب أن يعود `404` دون اسم المريض أو هاتفه. تغيير قيم `userId` أو `tenantId` في الرابط لا يغير النتيجة.
5. لمحاولة التعديل عبر واجهة البرمجة، افتح أدوات المتصفح ثم تبويب Network، وعدّل مريض **ب** التجريبي. اختر طلب التعديل، واستخدم Edit and Resend إن كانت متاحة. استبدل معرّف المريض في رابط الطلب بمعرّف مريض **أ** مع إبقاء جلسة **ب**. يجب أن يفشل الطلب، عادةً بـ`404`، وألا يتغير سجل **أ**. إدخال مالك غير مسموح مباشرة في عملية كتابة قاعدة البيانات يُرفض بـ`403` عند وصوله إلى الواجهة، مع الرسالة: `You do not have permission to access or change this record.`
6. داخل العيادة نفسها، يجوز لموظفين لهما صلاحية المرضى رؤية الملف المشترك. لكن فتح إشعار شخصي لموظف آخر أو تغيير تفضيلاته يجب ألا ينجح. مشاركة الملف السريري داخل العيادة سلوك مقصود.
7. جرّب حجزًا عامًا برقم هاتف ملف قديم: يجب أن يعرض التأكيد اسم الحاجز المدخل، ولا يكشف بيانات الملف القديم. رقم الحجز دون سر الإدارة يجب أن يعيد `404`.

## الاختبارات الآلية

نتائج التحقق المحلي: نجح 19 اختبارًا للعزل وسلامة الوظائف المسموحة، و10 اختبارات للجلسات وتسجيل الدخول، و213 اختبارًا لوظائف التطبيق، و3 اختبارات لبنيته. نجح بناء الحل دون تحذيرات أو أخطاء، وفحص تركيب Compose، وتشغيل أمر الترحيل الفعلي على قاعدة اختبار منفصلة. لم يُشغل Docker نفسه لعدم توفر محركه في هذه البيئة.

الملف `tests/DentalClinic.IntegrationTests/RowLevelSecurityTests.cs` يستخدم PostgreSQL فعليًا مع حساب لا يملك الجداول ولا يتجاوز RLS. يزيل بعض الاختبارات شروط التطبيق عمدًا، ويجرب الاستعلام برقم السجل وSQL مباشرًا، ليثبت أن المنع صادر من قاعدة البيانات.

```sh
dotnet test tests/DentalClinic.IntegrationTests/DentalClinic.IntegrationTests.csproj --filter FullyQualifiedName~RowLevelSecurityTests
```

يستخدم Docker وPostgreSQL 17 افتراضيًا. يمكن ضبط `RLS_TEST_POSTGRES` لاتصال خادم اختبار معزول بدل Docker. يحتاج هذا الاتصال صلاحية إنشاء قواعد وحسابات اختبار؛ لا توجهه إلى قاعدة الإنتاج. الاختبارات تنشئ قاعدة باسم عشوائي وتحذف قاعدة الاختبار وحساباتها بعد الانتهاء.

## الحدود المتبقية

- لم يترك الترحيل أيًا من الجداول الـ88 دون RLS. جدول تاريخ التحديثات التقني مستثنى كما سبق.
- التفعيل على قاعدة الإنتاج وتشغيل صور Docker لا يزالان مطلوبين على السيرفر؛ نجاح الاختبارات المحلية لا يعني النشر.
- صلاحيات أعمال التطبيق الدقيقة، مثل السماح بطباعة الروشتة، تستمر في طبقة التطبيق. RLS يفرض عزل العيادة وملكية البيانات الشخصية، ويحمي تعديل صلاحيات المستخدمين والروابط الحساسة داخل قاعدة البيانات.
- الأدوار الإدارية والخدمية المصرح بها تظل قادرة على الوصول اللازم لعملها؛ حساب المالك يتجاوز RLS بطبيعته، ولهذا فُصل عن خدمات الويب.
- قد ينتج عن الحجز العام أكثر من ملف للهاتف نفسه. لا يوجد تحقق من ملكية الهاتف عبر رسالة تأكيد في المشروع؛ لا يمكن اعتبار تطابق الهاتف تفويضًا لفتح ملف قديم.
- ملاحظة موجودة مسبقًا خارج تعديل RLS: ملف `DatabaseSeeder.cs` يتضمن كلمة مرور افتراضية لإنشاء حساب مدير المنصة عند غيابه. لم تُغير هذه المهمة بيانات دخوله الحالية. يجب التأكد من تغيير كلمة مرور حساب الإدارة قبل الإنتاج؛ صلاحية المدير مقصودة، ولذلك لن يمنع RLS شخصًا استطاع تسجيل الدخول بهذا الحساب.
- توقفت قاعدة الاختبار المحلية بعد التحقق. رفضت مراجعة الموافقة التلقائية حذف مجلد `tmp/rls-postgres-data` بسبب سياسة الأدوات، دون تقديم سبب أكثر تحديدًا؛ بقي المجلد المؤقت، ولا يحتوي بيانات إنتاج.
